# 平台授权参考（飞书 / 钉钉 / 企微）

三个平台走完全不同的授权机制，排查前先分清是哪一种。

## 飞书（Feishu / Lark）— 设备码流程

- `login()` 走 lark-cli 的设备流，CLI 输出里含一条设备验证链接（形如 `.../page/cli?<设备码参数>`）和一段 ANSI 彩色方块字符画的二维码。
- **坑**：字符画二维码被前端当纯文本、套主题色渲染会变灰蓝花块，看起来像乱码、扫不出来。
- **正确实现**：
  1. 后端用统一二维码生成函数，把链接渲染成**标准黑白 PNG**（如 `fill_color="black"`, `back_color="white"`，带标题），写入 `qrcode` 字段返回，并缓存到实例的 `_last_qrcode`。
  2. 前端 `login` 响应里若有 `qrcode`，优先显示 `<img>`；字符画 raw 只作文字备份。
  3. 清理 raw：正则去掉 ANSI 转义（`\x1b\[[0-9;]*[A-Za-z]`），删除整行仅由方块字符组成的行。
- 验证：PNG 像素接近纯黑白、三角定位完整、`/qr` 路由可取回、可扫码。

## 钉钉（DingTalk / dws）— OAuth loopback

- `dws auth login` 在本机起 loopback 监听，**主动打开系统默认浏览器**跳官方授权页（`login.dingtalk.com`），用户扫码确认后回调写回 token。
- 跳到外部浏览器是**设计如此、不可省**：授权页只能运行在官方域名，无法内嵌进大屏。
- 诊断命令：`dws auth status`，关注 `authenticated`、`token_valid`、`expires_at`。
- 只要 token 有效，无需重新授权；关掉浏览器页面无影响。

## 企业微信（WeCom）

- 走企业自建应用/扫码授权，凭证与回调配置由管理员在企微后台完成。
- 与飞书类似，若涉及二维码展示，同样优先用后端生成的标准黑白 PNG，避免字符画渲染。

## 通用要点

- 所有 token / user_code / 凭证都是**运行时秘密**，绝不写入日志以外的持久文件，绝不进 Skill。
- 授权状态展示（已授权/未授权/有效期）与"重新授权"按钮分离；重新授权会使旧设备码失效，提示用户。
- 二维码接口应能重复取回当前会话的图；重新登录后应生成新图并替换。
