# 踩坑与已验证修复（排错优先读）

按出现频率排序。每条含"现象 → 根因 → 修复 → 验证"。

## 1. 对话气泡加载慢 / 返回空消息

**现象**：点开某个大群会话，加载耗时数秒到十几秒，最终显示"该会话没有可显示的消息"。接口命中原始行数但返回消息数为 0。

**根因**：消息表用 `ORDER BY create_time DESC LIMIT n` 排序，而 `create_time` 列**没有索引**（索引通常只有 sort_seq / server_id / sender_id / type_seq）。SQLite 被迫全表排序，踩到明文库中个别损坏的 btree 页 → 抛 malformed → 被 `except: return []` 吞掉 → 返回 0 条。排序失败还会触发上层重试/等待，放大到数秒。

**修复**：消息分页排序优先选有索引的列，顺序：`sort_seq` → `rowid` → `local_id`，最后才退回时间列。`create_time` 仍作为输出字段用于显示时间，只是不拿它排序。

**验证**：同一会话从 ~10s/0 条 → 0.05s/60+ 条真实消息。可用 SQLite `PRAGMA index_list(<表>)` 确认哪些列有索引；对比 `ORDER BY create_time` 报 malformed 而 `ORDER BY sort_seq`/`rowid` 在毫秒级完成，即可确诊。

## 2. 中文标题发虚 / 带红蓝重影（ClearType 彩边）

**现象**：卡片标题里的中文字笔画糊成一团、边缘有彩色描边；英文却正常。

**根因**：为"提亮"把 CSS `font-weight` 提到 800，但中文用的字体（如 Microsoft YaHei）没有 800 字重，浏览器触发**合成加粗**，把中文笔画硬挤糊；英文（如 Segoe UI）有原生粗体所以正常。深色背景上 ClearType 次像素渲染又放大了彩边。

**修复**：
- 字重降到 700（目标字体原生支持的粗体），不要盲目上 800/900。
- 去掉 `text-transform:uppercase` 和过大的 `letter-spacing`（中文不需要，字距被拉开会发虚）。
- 加 `-webkit-font-smoothing:antialiased`、`text-shadow:none`、必要时 `transform:translateZ(0)` 走 GPU 合成消除彩边。

**验证**：放大截图对比修复前后"会/话"等字，笔画应干净无重影。

## 3. 标题/小字太暗看不清（深色主题对比度）

**现象**：黑色系界面里，"自动刷新/搜索方式/结果排序""上次同步/本轮新增/累计轮次"及流程说明等小字几乎看不见。

**根因**：用了低亮度主题变量（近似 `#5d6c85`）+ 10.5px 小字号。

**修复**：这类辅助文字提到 `#b9c8de` 级别、12px 左右、字重 600；卡片主标题用接近纯白（如 `#f2f6ff`）。保持层级但保证可读。

## 4. 全屏大屏窗口要么秒关、要么抓不到真实画面

**窗口秒关**：不要在命令行直接 `python launch_big.py` 启动浏览器——那样 Chrome 是调用进程的子进程，调用方退出会被沙箱回收。必须由**服务进程**调 `GET /api/screen`，在 server.py 内起线程调用 `launch_big.open_window()`。Chrome 用 `--app=<url>` 模式：无标签栏、无地址栏、`0,0` 铺满全屏。

**截图验收**：Windows 前台锁定导致 `ImageGrab` 常抓到前台的其他窗口；`PrintWindow(hwnd, hdc, 2)`（PW_RENDERFULLCONTENT）对 Chrome 的 GPU 渲染又可能抓成白屏。可靠做法：用窗口标题定位 hwnd → `SetWindowPos(HWND_TOPMOST)` 置顶 → 短暂 `sleep` → `ImageGrab.grab(all_screens=True)` → 恢复非置顶。按标题匹配 + 宽 > 1000 过滤出真正的 `--app` 窗（可能同时存在带标签栏的普通窗）。

## 5. 服务反复重启 / 双实例 / 端口占用

**现象**：日志大量 `watchdog ... restarted`；`api/*` 偶发超时；同步循环 age 突然拉长。

**根因链**：
- Windows `SO_REUSEADDR` 允许两个进程同时绑 7890，"能否绑定"不能当唯一实例判据。双实例会同时跑增量刷新、互相替换库文件。
- 多个 watchdog 各自守一个 server.py → 无限重启风暴。
- server.py 异常退出码（如 -1/4294967295）被 watchdog 当作需重启。

**修复**：
- `boot.py` 加单例锁，只允许一个 watchdog。
- 启动前按命令行（含 server.py 且工作目录匹配）全量清理残留实例，排除自身。
- watchdog 常驻，`p.wait()` 异常不得退出 watchdog；对非 3/4 退出码重启，带退避和端口等待。

## 6. 自动同步间隔 tweaking 反而更慢

**现象**：想让数据加载更快，把自动增量刷新间隔从 20s 调到 8s，结果对话加载更卡、耗时波动更大（0.04s~30s）。

**根因**：源库被微信持续写入，每轮刷新都要复制/替换一个大库（数百 MB）。刷新越频繁，读请求撞上替换窗口的概率越高，被文件闸门阻塞。间隔 8s 反而放大了碰撞。

**修复**：把间隔调回温和值（20s 或更长）；前端轮询空闲间隔也别低于后端同步间隔太多。真正该优化的是消除无谓替换（`changed==0` 时不替换，多数实现已具备）与规避撞窗，而非提高刷新频率。代码里通常有下限 `max(5, int(interval))`。

**结论**：遇到"加载慢"先分清是统计/同步节流、还是查询排序、还是替换撞窗，别一律调快刷新。

## 7. 大库 os.replace 偶发失败

**现象**：日志 `xxx.db: os.replace 重试 N 次仍失败`，但几秒后下一轮正常。

**判断**：多为间歇性文件占用；若下一轮 cycles 递增、changed 正常，则不阻塞数据，可不修。若持续失败，检查是否有连接句柄未纳入"替换前统一关闭"的映射（走通用分支打开的连接容易漏登记，导致替换时文件仍被占用）。

## 8. 飞书授权二维码显示为灰蓝花块（像乱码）

**现象**：授权弹窗里链接文字正常，但二维码是灰蓝/深色花块，扫不出来。

**根因**：飞书设备流登录接口只返回链接和原始输出，不返回二维码图片。前端只能把 CLI 输出里的**ANSI 背景色字符画二维码**当纯文本渲染，套上主题色（灰蓝）就成了花块。后端其实有标准二维码生成器却没被调用。

**修复**：
- 后端登录时用现成的二维码生成函数把链接渲染成标准黑白 PNG，作为 `qrcode` 字段返回并缓存；前端优先显示该图。
- 清理 raw 输出：去掉 ANSI 转义序列，删除整行只由方块字符（`█▀▄▌▐■□`）组成的字符画行，只留文字链接。

**验证**：接口返回纯黑白 PNG（像素值接近 0/255）、三角定位完整、带标题，`/api/platform/qr` 可取回，可正常扫描。

## 9. 钉钉授权"跳到外部浏览器"

这是**正常且必需**的。钉钉走 OAuth loopback：本地起监听 → 主动打开系统默认浏览器跳官方授权页 → 用户扫码确认 → 回调打到本机端口写回 token。授权页只能是官方域名，塞不进大屏。不要试图"修复"成内嵌。诊断时看 `dws auth status` 的 `authenticated`/`token_valid` 即可。

## 10. 署名/排版迭代经验

- 署名与标题**并排**显得挤，放标题**正下方居中**、间距约 11px 更协调。
- 主入口（浅色页）署名放内容卡片下方空白处做页脚，居中、灰绿色，低调不挡操作。
- 署名是可配置的作者标识，重建时按用户提供的值填写；它不是隐私数据，但也不应被硬编码进"通用知识包"的具体值里。

## 11. 全库搜索卡死服务 / 中文文件名下载中断

**症状**：搜索关键词后整个 HTTP 服务无响应（HTTP 000），某 python 进程内存涨到 1.2G；或一键整理下载 docx 时 `IncompleteRead`、curl 报 "Header without colon"。

**根因**：
- 微信 4.x 有 6404 张 `Msg_<md5>` 分表、248 万条消息。原 `db.search()` 全库检索 = 逐表 `LIKE '%kw%'`，串行扫全部分表 → 内存/CPU 爆掉、服务假死。
- Python 的 `BaseHTTPRequestHandler.send_header` 用 latin-1 编码响应头，中文文件名直接写 `filename="中文.docx"` 会抛异常 → 响应头残缺、连接中断。

**修复**：
- 用 `search_fts.py` 一次性把所有消息文本抽到独立 FTS5 索引库（trigram，约 94 万条/1 分钟），之后搜索走索引毫秒级；≥3 字符用 MATCH，1~2 字符回退单表 LIKE。索引存在即复用，**不要**因增量刷新导致的文件大小/mtime 变化反复重建（否则每次重启都重建 1 分钟）；刷新交给显式 `/api/search/rebuild`（force）。
- `send_file` 用 RFC5987 `filename*=UTF-8''<urlencoded>` 编码中文名，并给 ASCII 兜底 `filename`；前端按 `filename*=UTF-8''` 解析并 `decodeURIComponent`。
- docx 用 `digest_docx.py` 零依赖生成（标准库 zipfile + 最小 OOXML），不装 python-docx，跨平台。

**验证**：搜 ≥3 字关键词应 <0.2s 且 `source=index`；`/api/digest?q=关键词` 返回合法 docx（zip 完整、XML 可解析、中文名正确）。

## 12. 对方 clone 后"一键提取密钥"永远失败（漏打包 + 走了单密钥老路径）

**症状**：别人 clone 仓库、装好、能打开解密入口页，也**能**探测到加密库（"已找到加密数据库（20 个）"），
但一点"⚡ 一键探测 + 解密 + 加载"就停在"但是要密钥"；点"🔑 从微信进程提取"也不出密钥，
提示只有一句"未能自动提取（微信版本/权限限制）"——像版本不兼容，其实是包里没代码。

**根因（两层，叠加才会这么难查）**：
1. **漏打包**：`keycap.py`、`wcdb_ctx.py` 没进仓库（也不在 git 历史里）。前者是跨平台密钥捕获入口，
   后者是 SQLCipher codec 上下文解析 + 页 1 HMAC 校验的全部实现。缺了它们，
   `decrypt.extract_keys_v4()` → `import keycap` 直接 ImportError，一键提取必然失败。
   同理漏掉的还有 `sample.py`（`/api/sample` 示例库），少了"先看效果"这条路。
2. **入口接错**：`/api/key-extract` 和 `/api/auto` 原本走 `decrypt.extract_key_from_process()`
   —— 老的 Windows-only 高熵暴力扫描，`os.name != "nt"` 直接 `return None`，且**只能出一个 key**。
   而 4.x 每个 `.db` 有自己的 salt + key，单 key 最多解开 1 个库。于是即便有密钥，
   20 个库里 19 个也解不开。真正正确的链路（`accounts.decrypt_account` → `extract_keys_v4` →
   `decrypt_account_v4` 按 salt 逐库取 key）一直存在，只是没接到按钮上。

**修复**：
- 补齐三个模块；`/api/key-extract` 改走 `accounts.ensure_keys()`（逐库 key + 写入 keyring），
  老的暴力扫描降级为兜底；`/api/auto` 不带 key 时不再直接甩"需要密钥"，而是起
  `start_decrypt_account()`（keyring 复用 → 缺的补提取 → 逐库解密）。
- 前端把真实 `reason` 显示出来（以前一律写"微信版本/权限限制"，缺模块/未登录/权限不足全长得一样，只能靠猜）。
- 新增 `scripts/preflight.py`：必需文件清单 + 扫"被 import 但没打包"的模块 + 逐模块 import。
  发布前必跑；缺文件时它会直接点名 `keycap.py` / `wcdb_ctx.py`。

**验证**（干净副本、空 keyring）：
`python scripts/preflight.py --imports` 22 个模块全绿；
`GET /api/key-extract` 从运行中的微信进程提取到 44 个逐库密钥；
拿其中 2 个库跑 `decrypt_account_v4` → `2/2 OK`，产物 `sqlite_master` 可读。

**教训**：打包只能**整目录 copy**，不要按白名单挑 `.py`；每加一个模块就把它写进 `preflight.py`
的必需清单。另一个教训：入口函数要指向"最新的那条链路"，老实现别留着当门面——
留着就必须在 UI 上把失败原因透出来。

## 13. 解密页的「📺 大屏」跳到 7391 打不开（要输 PIN / 404）

**症状**：点解密入口页的「📺 大屏」，打开的是 `http://127.0.0.1:7391/bigscreen.html`，要求输编码或直接 404；手动把端口改成 7890 就正常。装包的人一头雾水，以为是没装好。

**根因**：`server.py` 里 `CFG` 的默认值写死过 `"bigscreen": "http://127.0.0.1:7391"`。
7391 是**开发机上的 CodeScreen 反代入口**（带 PIN 保护），作者本机 `config.json` 覆盖成 7890，所以本地永远正常；
别人 fresh install 没有 `config.json`，拿到的就是这个默认值。前端又有一条"配置指向别处就按配置走"的分支
（`base.indexOf(location.origin) !== 0`），于是老老实实拼出 7391 的链接。

**修复**：
- 默认改为**空串 = 跟随当前页面（同源）**：直连 7890 得 `/bigscreen.html`，走 `/wa/` 反代得 `/wa/bigscreen.html`，
  用局域网 IP 打开就得局域网地址，全部自动正确，不用配。
- 前端加护栏：配置里的地址若是本机回环（`127.0.0.1` / `localhost` / `[::1]` / `0.0.0.0`）
  但 origin 与当前页面不同，**一律忽略并 console.warn** —— 专治"别人机器上残留了作者这边的 config.json"。
- 显式配置成非回环地址（隧道、局域网、域名）时仍然尊重配置。

**验证**（无 config.json 的全新副本）：点大屏 → `/bigscreen.html`；POST 残留 `127.0.0.1:7391` → 仍走同源；
POST `192.168.1.9:7890` → 按配置走；清空 → 回到同源。

**教训**：**开发机的本地状态（端口、反代地址、路径）一个都不能进默认值**。默认值必须是"在任何机器上都成立"的那个。

## 14. 大屏里点「← 返回解密」后，全屏窗口"消失"，再点「📺 大屏」只开出浏览器标签页

**症状**：在 `--app` 全屏窗口里点「← 返回解密」→ 窗口不见了（没标题栏、任务栏也没图标，
Alt+Tab 里也难找），再点首页的「📺 大屏」得到的是一个**普通浏览器标签页**，
不是原来那个铺满全屏的窗口。

**根因**：`--app` 窗口就是一个浏览器窗口，`location.href` 导航到首页后，它**仍然是那个窗口**，
只是不再显示大屏；而首页的「📺 大屏」用的是 `window.open(url,'_blank')`，
它只会开新标签页 —— 于是"大屏"这个形态丢了，用户以为窗口消失了。

**修复**：
- `launch_big.add_appwin()` 给大屏地址加 `appwin=1`；大屏页的「返回解密」把它带到首页
  （`index.html?appwin=1#decrypt`）。首页看到这个标记就用 **同一个窗口** 跳回
  `/bigscreen.html?appwin=1`，全程不 `window.open`。
- 普通浏览器里点「📺 大屏」→ 请求 `/api/screen`，由**服务端**拉起真正的 `--app` 全屏窗口；
  `launch_big.focus_existing()` 先按标题找已有窗口，找到就提到前台（不会越点越多）。
- `TITLE_HINT` 收紧成 `微信数据分析 · 大屏`：原来用 `微信数据分析` 会把标题为
  「微信数据分析 · 精简版（只读）」的普通浏览器标签页当成大屏窗口"聚焦"过去。
- 顺带补 `/api/screen/close`（Win32 `WM_CLOSE`）+ 前端「✕ 关闭」：
  `--app` 窗口没标题栏、任务栏也没图标，直连 7890 时原来根本关不掉，只能 Alt+F4。

**验证**：headless Chrome 实测 —— `index.html?appwin=1` 点大屏 → 同一个标签页变成
`bigscreen.html?appwin=1`（页面数 1→1）；大屏点返回 → 同一个标签页回到
`index.html?appwin=1`（标记不丢）。真机日志：`[大屏] 拉起窗口: .../bigscreen.html?appwin=1`。

## 15. 大屏窗口 + 浏览器标签同时打开，两边一起显示「同步异常」

**症状**：Agent 拉起全屏大屏后，又把同一个链接粘到浏览器打开；两个页面同时显示
数据链路「同步异常」，关掉一个才恢复。

**根因**：每个页面都自带一个 180s 的 `autoRefresh()`，会各自调 `/api/refresh` 触发增量解密；
服务端守护线程另外每 20s 也刷一次。多个客户端 = 多套触发源，抢同一个明文库的
Windows 文件锁（`os.replace` 时 SQLite 句柄未释放 → `PermissionError`）。
另外单轮失败很常见（微信正在写源库），但旧逻辑只要有一轮失败就置 `last_error`，
界面立刻变红且要等下一轮成功才恢复，看起来像"两个一起打开就坏"。

**修复**：
- `/api/dash` 已带 `auto_refresh.running`；前端记住 `SRV_SYNC`，**服务端在自动同步时
  客户端不再触发刷新** —— 一个进程只有一套同步节奏，开几个页面都不互相干扰。
- 服务端 `err_streak`：连续 2 轮失败才置 `last_error`（单轮抖动自己会好），
  成功一轮即清零。`/api/dash` 输出 `err_streak` 便于排查。

**验证**：重启后连测 50s，`cycles` 1→4 稳定推进，`last_error` 为空、`err_streak` 0。

## 16. 关键词里带 `-` `:` `+` 就"搜不到"（FTS5 把关键词当查询语法）

**症状**：搜 `personnel-registration`、`134:8099`、`C++` 一律 0 条，但库里明明有
（`LIKE '%…%'` 能查到 2 条）。纯中文、纯字母数字的关键词都正常，所以很容易被当成"索引没建好"。

**根因**：`fts MATCH ?` 收到的是**查询语法**，不是字面量。
- `-` 是列过滤/差集语法：`personnel-registration` → `no such column: registration`
- `:` 是列过滤：`134:8099` → `no such column: 134`
- `+` `*` `"` `(` `)` 与裸 `AND`/`OR`/`NOT` → `syntax error near …`

`search()` 当年把 FTS 查询和 LIKE 兜底包在**同一个** `try` 里，异常直接跳到
`except Exception: pass`，**LIKE 兜底根本没执行**，于是静默返回 0 条 —— 复现率 100%，
但只在关键词含语法字符时出现。

**修复**（`search_fts.py`）：
- 新增 `_fts_query()`：按空白切词，**每个词包成短语**（内部 `"` 按 FTS5 规则双写），
  词间用 `AND` 连接。特殊字符一律降级为字面量，多词语义不变。
- FTS 查询单独 `try/except sqlite3.Error`，出错只清空结果并落回 `msgs` 单表 LIKE，
  绝不再把"语法错误"包装成"没搜到"。

**验证**（生产索引 248 万条 / 154MB，修复前后对比）：

| 关键词 | LIKE 真值 | 修复前 | 修复后 |
|---|---|---|---|
| `personnel-registration` | 2 | 0 | 2（0.02s） |
| `134:8099` | 2 | 0 | 2（0.01s） |
| `手绘-贴图` / `a-b` / `AI:批量` / `进度:50%` / `C++` / `AND` | 各 1 | 0 | 各 1 |
| `测试` / `合同` | 927 / 198 | 正常 | 正常（0.14s） |

**教训**：凡是"把用户输入拼进某种查询语言"的地方（SQL / FTS / 正则 / DSL），
必须先转义或参数化；兜底分支必须与失败分支**分开** `try`，否则兜底永远等不到执行。

## 17. "包只适配 4.1.13，4.2.0 改了 WCDB 布局"——这个结论是错的

**症状**：对方在 4.2.0.53 上取不到密钥，于是判定"`wcdb_ctx.py` 的解析偏移是按 4.1.13 写死的，
4.2.0 改了内部布局，属密码学层面的版本不兼容，只能逆向 4.2.0"。

**实测结论**：在**同一台 4.2.0.53** 机器上，本包原版 `wcdb_ctx.py`（`CODEC_PREFIX` 特征 +
`0x48/0x50/0x68/0x70` 偏移 + 32 字节 pad 推导）仍然有效：

```
微信版本 4.2.0.53
取样 session.db / contact.db / favorite.db / bizchat.db / message_0.db / message_1.db …
结果 8/8 个库密钥实证通过（页 1 HMAC-SHA512 校验 True）
```

4.2.0 并没有改动 codec 上下文的这些偏移；"0 个密钥"的真因通常在这几处：
① 微信没运行/未登录（内存里没有密钥）；② 不是同一系统用户或权限不足；
③ **对方自行"重建"过 `wcdb_ctx.py`**（这正是踩坑 12 里发生的事）——近似实现偏移错位，
读出来的"salt"其实是别的数据。

**应对**：判据换成**密码学实证**，不再靠版本号推断。新增 `scripts/keycheck.py`：
一条命令打印「微信版本 → 加密库 → 每库 salt → 页 1 HMAC 是否通过 → 仓库是否干净」。
对方再报"取不到密钥"，先让他跑这个并把输出贴回来，别先下"版本不兼容"的结论。

**教训**：跨版本兼容性要用**实证**（HMAC/试解密）判定，不能用版本号推；
同时"对方自己改过代码"必须纳入排查清单，否则会把自家改动误判成上游不兼容。
